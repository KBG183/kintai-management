07 / BACKEND · CONCURRENCY

同一スタッフによる連続打刻リクエストを
DB悲観的ロックにより二重登録を完全防止。

ネットワーク遅延や連打によって出勤(CLOCK_IN)リクエストがミリ秒単位で多重到達した際に生じるレースコンディションを根本から防止しました。

RACE CONDITION RISK

同時到達時の二重生成リスク

リクエストA・Bが同時到達 → 双方とも既存出勤なしと判定 → 出勤行が2件INSERT!

勤務状態の不整合が生じ、当日の勤務時間が二重計上される重大なデータ破損が発生

PESSIMISTIC LOCK FIX

親行(store_staff)の悲観的排他ロック

SELECT ... FOR UPDATE → トランザクションを直列化 → 先行1件成功・後続1件は重複拒否

後続リクエストは先行処理完了後に最新状態(WORKING)を検知し、409 Conflictで安全に遮断

検証方式新規隔離DB 3箇所にて同一スタッフのCLOCK_IN・CLOCK_OUT競合スレッド反復テスト
実行結果並行性結合テスト 計6/6 PASS（二重レコード生成 0件）を実証

検証実測値同一スタッフ出退勤同時リクエスト 6/6 全件において1件成功・1件拒否の正常直列化を確認

08 / BACKEND · SECURITY

クライアント送信の職員IDは信頼せず、
サーバーセッションのPrincipalでのみ身元を認証。

APIリクエスト本文(JSON)のstoreStaffIdを他人のIDに書き換えて他者の勤怠を代理打刻・不正閲覧するIDOR（安全でない直接オブジェクト参照）攻撃を防御しました。

IDOR VULNERABILITY

リクエスト本文パラメータ依存の脆弱性

ログインスタッフA → 本文にスタッフBのIDを改ざん送信 → Bの勤怠が改ざんされるリスク

認証済みアカウントと実際の処理対象エンティティの所有権検証が乖離するセキュリティ事故

PRINCIPAL DEFENSE

Spring Security セッションバインド

SecurityContextからPrincipalを抽出 → DB上の所有権を照合 → 不一致時は即時403遮断

クライアントが送信した本文IDは破棄し、サーバーセッションで認証済みの職員識別子のみを使用

0 IDOR他者勤怠の改ざん可能性を完全排除
403 FORBIDDEN不正パラメータ改ざん時の即時アクセス遮断
RBAC 分離店長・スタッフのアクセス境界を厳格隔離

検証実測値悪意あるstoreStaffId改ざん打刻に対する結合セキュリティテスト全件403遮断PASSを確認

09 / BACKEND · DEADLOCK

給与一括確定と個人再計算の競合、
ロック取得順序を統一しError 1213を解消。

月末に店長が全スタッフの給与を一括確定(Batch Confirm)する処理と、個別スタッフの給与再計算が同時に実行されたことで発生したMySQL InnoDBデッドロックを解決しました。

DEADLOCK OCCURRENCE

逆順ロックによる相互待機

トランザクションA: payroll_id 13ロック保持 → store_staff_id 1ロック待ち
トランザクションB: store_staff_id 1ロック保持 → payroll_id 13ロック待ち

MySQLエンジンがデッドロックを検知し、Error 1213と共にトランザクションBを強制ロールバック

2-PHASE ORDERED LOCK

親行からID昇順ロック

第1段階: 確定対象のstore_staffをID昇順で先行してFOR UPDATE
第2段階: 親ロック完了後にpayroll子行を順次処理

すべてのトランザクションのロック獲得方向を単一方向に揃え、デッドロックの発生条件そのものを根絶

ロック獲得順序を親行から一方向に統一した結果、高負荷デッドロック再現テストにおいて1213エラーが100%解消されました。

実測ログ証跡MySQL InnoDB Deadlock (Error 1213) 原文解析および2段階整列ロック適用後の競合解消を確認

13 / VERIFICATION · THE REAL RISK

AIが作成したソースコードを
AI自身に自己点検させてはならない理由。

LLMは流暢でありながら誤ったコードを出力することがあり、対話コンテキストが長引くほど最初の誤謬を前提として盲信する構造的限界を抱えています。

RISK 01 · HALLUCINATION

幻覚 (Hallucination)

実在しないAPI構文や誤った労働法規の計算式をあたかも正解であるかのように精緻に出力

RISK 02 · CONTAMINATION

コンテキスト汚染

直前の対話における誤った前提や見落としを、後続の実装や自己レビューでもそのまま踏襲

RISK 03 · SELF-REVIEW BIAS

自己検証の限界

コードを生成した同一モデル・同一コンテキストでは、自分自身の論理的欠陥を再発見できない

だからこそ、コードを実装するAIと、欠陥を炙り出す監査AIを物理的に完全隔離しました。

AIの支援を受けつつも、最終的な合否判定は物理的な実行結果（テストコード・ログ）のみで行う原則を確立

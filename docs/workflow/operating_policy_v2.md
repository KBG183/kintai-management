# 프로젝트 운영 정책 v2

## 1. 역할 분리

- Antigravity: 구현, 테스트 실행, 증적 수집, Hermes/Qwen 27B 감사 요청
- Qwen 27B: 구현 주체와 독립된 블라인드 감사
- Codex: 사용자 요청이 있을 때만 파일·로그·테스트 결과·감사 결과를 추가 검토하는 선택적 검수자
- 사용자: 요구사항, 범위, 최종 승인

Codex는 자동으로 호출하지 않으며, 사용자가 명시적으로 요청한 경우에만 작업에 참여한다. Codex에서 원격 Tailscale Qwen을 파일 큐로 직접 호출하는 방식은 주 운영 경로로 사용하지 않는다. Antigravity의 기존 Hermes 자동 감사 경로를 우선한다.

Kintai에서 번들 감사 시 `scripts/audit_hermes_preflight.ps1`을 사용하고 입력 매니페스트를 전달한다. 직접 Hermes를 호출하면 이 검사가 우회된다. 이는 운영 지침이며 시스템 전체에 물리적으로 강제된 통제는 아니다. 입력 또는 증적이 없어 검사를 진행할 수 없으면 임의의 자료로 채우지 않고 사유와 미검증 범위를 기록한다.

## 2. 작업 단위

Day 중간의 불필요한 반복 감사는 피한다. 기능·보안·급여·동시성 변경은 관련 테스트와 Qwen 독립 감사를 수행하고, 문서 정리 등 저위험 변경은 범위에 맞는 확인을 수행한다. 감사가 필요한 작업을 수행하지 못하면 사유와 범위를 기록한다. 다음은 기능 개발에 적용하는 기본 사이클이다.

1. SRS·AGENTS·RTM 기준 확인
2. 구현 또는 필요한 테스트 작성
3. 로컬 환경에서 결정론적 테스트 실행
4. 원본 로그와 JUnit XML 보존
5. 한·일 증적서 초안 갱신
6. Qwen 27B 독립 블라인드 감사
7. 지적사항 수정 및 재감사
8. 최종 회귀 테스트와 무결성 확인
9. `IMPLEMENTED`, `VERIFIED`, `BLOCKED`, `PARTIALLY_VERIFIED` 판정
10. 사용자가 Codex 검수를 요청한 경우에만 Codex 추가 검토 수행

## 3. 완료 판정 규칙

Codex 검수는 기본 완료 조건이 아니다. Antigravity와 Qwen, 결정론적 테스트와 원본 증적만으로도 작업을 완료할 수 있다. 다음 경우에만 사용자가 Codex 검수를 선택적으로 요청한다.

- Antigravity와 Qwen의 판정이 서로 다를 때
- 보안·트랜잭션·데드락·데이터 손상처럼 위험도가 높은 변경일 때
- 사용자가 최종 교차검수를 원할 때
- 이전 증적이나 파일 이동의 정합성을 다시 확인할 때

상태 정의와 증적 요구사항은 `docs/workflow/evidence_status_policy.md`를 기준으로 한다.

실제 실행하지 않은 테스트를 성공으로 기록하지 않는다. 로컬 MySQL 26.7 결과와 MySQL 8.4 결과를 혼합하지 않는다.

## 4. 증적 우선순위

```text
실행 명령
→ 원본 콘솔 로그
→ JUnit XML 및 DB 결과
→ Qwen 감사 결과
→ 한국어·일본어 증적서
→ 최종 판정
```

보고서와 원본 증거가 다르면 원본 증거를 우선한다.

## 5. 파일 정리 규칙

- 활성 문서와 과거 보관 문서를 분리한다.
- 파일을 이동한 뒤 자동화 스크립트와 문서의 이전 경로 참조를 확인한다.
- 이동 전후 SHA-256을 비교한다.
- 이동된 파일은 Git 상태에서 삭제와 신규 파일로 보일 수 있으므로 유실 여부를 별도로 확인한다.
- 활성 경로는 `docs/workflow/project_paths.md`에 기록한다.
- 인코딩과 줄바꿈 변경은 내용 변경과 별도로 기록한다.

## 6. 증적서 갱신

한국어 증적서와 일본어 증적서는 같은 작업 결과를 병행 갱신한다. 각 항목에는 Day 번호, 요구사항 ID, 실행 명령, 실제 결과, 테스트 식별자, 판정, 제한사항을 포함한다.

- 기존 두 자리 개정 표기(`v1.09`, `v1.10`)와 한·일 동기화를 유지한다. 개정 번호와 Day 번호를 자동으로 동일하게 간주하지 않는다. 기존 이력에는 같은 날짜의 여러 개정이 존재한다.
- 진행 중인 같은 개정판에 추가한 기록과 정식 새 개정을 구분하고, 새 개정 시 양쪽 개정 이력에 같은 범위와 날짜를 기록한다. 실행하지 않은 작업이나 승인되지 않은 결과를 개정 이력에 완료로 기재하지 않는다.
- Qwen 감사 결과 원문은 수정하지 않고 보존한다. 별도 요약 또는 후속 검토에서는 `Finding ID`, 감사 항목, 심각도, Qwen 원래 판정, 코드·테스트 근거, 분석·조치를 연결한다. Qwen 판정과 실행 테스트 결과는 별도로 적는다.

## 7. 최종 확인 체크리스트

- 요구사항 ID와 RTM 연결이 양방향인가
- 구현과 검증 상태가 구분되어 있는가
- 대상 테스트가 실제 실행된 것이 맞는가
- 실패한 1차 시도와 수정 내용이 보존되어 있는가
- Qwen 감사가 독립 입력으로 실행되었는가
- 원본 로그와 JUnit XML이 존재하는가
- 한·일 증적서의 핵심 수치가 일치하는가
- SHA-256과 실제 파일 바이트가 일치하는가
- 환경 제약이 `BLOCKED`로 분리되어 있는가

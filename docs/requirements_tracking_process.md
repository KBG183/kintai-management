# AI 개발·감사 작업 수행 프로세스 (Requirements Traceability & Evidence-Based Verification Standard)

> **핵심 원칙**:
> 1. 작업 착수 전 지시사항을 R-01, R-02... 고유 ID로 전수 분해한다.
> 2. `IMPLEMENTED`(구현됨)와 `VERIFIED`(물리적 증거 충족)를 절대 혼동하지 않는다.
> 3. 증거(실제 실행 로그, 종료 코드, 원문 파일, JUnit XML, DB 실측치) 없는 완료 판정을 엄격히 금지한다.
> 4. 이미 검증된 작업의 불필요한 재수행을 방지하고 실패 이력을 보존한다.
> 5. 최종 독립 감사를 거치기 전에는 전체 완료를 절대 선언하지 않는다.

---

## 1. 요구사항 상태 정의
- **`NOT_STARTED`**: 미착수
- **`IMPLEMENTED`**: 코드는 작성되었으나 물리적 증거(테스트 실행, DB 검증)로 확인되지 않음
- **`VERIFIED`**: 사전에 정의된 완료 기준, 실행 명령, 종료 코드, 실제 출력 결과까지 100% 충족
- **`BLOCKED`**: 환경(예: MySQL 8.4 별도 인프라 부재 등)이나 선행 조건 미비로 진행 불가
- **`NOT_APPLICABLE`**: 명확한 기술적 근거와 사용자 승인에 따라 적용 제외

---

## 2. 7단계 운영 라이프사이클
1. **[요구사항 분해]**: 지시 접수 즉시 R-XX ID 부여 및 완료 기준(DoD), 필요 증거 정의
2. **[추적표(RTM) 관리]**: `docs/rtm_ledger.md`를 단일 진실 공급원(SSOT)으로 운용
3. **[증거 수집]**: 실행 명령, 종료 코드, 콘솔 출력, JUnit XML, DB 스냅샷을 고유 파일로 보존
4. **[실패 이력 보존]**: 중간 실패를 덮어쓰지 않고 실패 원인과 수정 조치 내역을 함께 기록
5. **[기존 검증 재사용]**: 이미 VERIFIED인 항목은 무효화되지 않는 한 불필요하게 재실행하지 않음
6. **[독립 감사]**: 요구사항과 실측 증거를 대조하여 미진한 항목이 1건이라도 있으면 미완료로 판정
7. **[표준 11대 보고서 출력]**: 전체/상태별 개수, 증거 위치, 회귀 결과, 잔여 위험을 규격에 맞춰 보고

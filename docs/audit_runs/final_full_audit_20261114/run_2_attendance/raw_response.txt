| AUD-001 | Japanese Labor Standards Act Art 37: Night Work & Overtime Calculation Logic | P0 | FAIL | `AttendanceService.java` (lines 108-115, 236-243), `AttendanceMapper.xml` (`sumPriorNetWorkSecondsOnDate`), `LaborCalculationService.java` | **Critical Logic Flaw in Overtime Accumulation**: The code attempts to handle "split shifts" (multiple attendance records per day) by summing prior net work seconds (`sumPriorNetWorkSecondsOnDate`) and passing it to `AttendanceTimeCalculator.calculate`. However, the SQL query `sumPriorNetWorkSecondsOnDate` calculates net time as `TIMESTAMPDIFF(SECOND, clock_in_at, clock_out_at) - (total_break_minutes * 60)`. This calculation is **incorrect** for determining overtime eligibility under Japanese Labor Law Article 37. Overtime is determined by the *total* hours worked in a day exceeding 8 hours. The current logic subtracts breaks from the raw duration, which is correct for *net work time*, but the critical failure is that `AttendanceTimeCalculator` (not fully visible but inferred from usage) likely treats the `priorWorkSeconds` as a simple offset. If the calculator does not correctly aggregate the *total* daily hours across multiple sessions to determine the 8-hour threshold before applying the 25% premium, the overtime calculation will be wrong. Furthermore, the SQL `TIMESTAMPDIFF` returns seconds, but `total_break_minutes` is in minutes. The subtraction `seconds - (minutes * 60)` is mathematically sound for net seconds, BUT if `total_break_minutes` in the DB is rounded or stored differently than the precise break intervals, discrepancies arise. More critically, the `AttendanceTimeCalculator` must be verified to ensure it adds `priorWorkSeconds` to the current session's net time *before* checking the 8-hour threshold. If it checks the threshold per-session, it will fail to trigger overtime for split shifts that individually are <8h but collectively >8h. |
| AUD-002 | Japanese Labor Standards Act Art 37: Night Work (22:00-05:00) Deduction of Breaks | P1 | WARN | `AttendanceService.java` (`handleClockOut`), `AttendanceMapper.xml` (`sumPriorNetWorkSecondsOnDate`) | **Night Work Break Deduction Ambiguity**: The requirement states "Break time between 22:00~05:00 must be deducted specifically from night work hours." The code passes `breakIntervals` to `AttendanceTimeCalculator.calculate`. It is assumed the calculator correctly subtracts break time from the night work window. However, the `sumPriorNetWorkSecondsOnDate` query only sums *net* work seconds. It does not provide the *night work* seconds of prior sessions. If a staff member works a split shift where the first session ends at 23:00 and the second starts at 23:30, the `priorWorkSeconds` passed to the calculator for the second session will include the night work hours from the first session. The calculator must correctly attribute these prior seconds to the "Night Work" bucket if they fall within 22:00-05:00. The current data structure (`priorWorkSeconds` is a single long) loses the temporal distribution of those prior hours. The calculator cannot know if the prior 4 hours were worked during the day or at night. **Recommendation**: Pass prior *night work seconds* and prior *overtime seconds* separately, or pass the full list of prior attendance intervals to the calculator for accurate bucketing. |

| AUD-004 | Concurrency & Security: Pessimistic Locking Scope | P1 | WARN | `AttendanceService.java` (`punch`, `requestModification`, `reviewModification`), `AttendanceMapper.xml` (`lockStoreStaffForUpdate`) | **Lock Scope Mismatch**: The code uses `attendanceMapper.lockStoreStaffForUpdate(storeStaffId)` to acquire a pessimistic lock on the `store_staff` table. This prevents two transactions from modifying the *same staff's* attendance simultaneously. However, in `reviewModification`, the lock is acquired on `req.getStoreStaffId()`. This is correct for preventing concurrent modifications to the same staff's attendance. However, the `updateModRequestReview` uses a CAS (Compare-And-Swap) pattern (`WHERE approval_status = 'PENDING'`). This is good. But the lock on `store_staff` is released when the transaction commits. If the transaction is long-running, it holds the lock. More importantly, does `lockStoreStaffForUpdate` prevent *other* staff from punching in? No, it only locks the specific staff row. This is correct behavior. However, there is a potential race condition in `punch`: `findActiveAttendance` is called *after* the lock. This is correct. But what if two requests for the *same* staff arrive simultaneously? The first acquires the lock, the second waits. The first inserts/updates, commits, releases lock. The second acquires lock, reads new state. This is correct. **Verdict**: PASS for basic concurrency, but verify that `store_staff` table has an index on `store_staff_id` to ensure the lock is efficient and doesn't escalate to a table lock. |

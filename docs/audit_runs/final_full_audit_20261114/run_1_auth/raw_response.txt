| F-001 | IDOR Vulnerability: Member Access Control | P0 | FAIL | `MemberController.java` (Line 58-63): `@PreAuthorize("hasRole('ADMIN') or #id == authentication.principal.memberId")` | **Critical Logic Flaw**: The SpEL expression `#id == authentication.principal.memberId` is flawed. `authentication.principal` in Spring Security is typically the `UserDetails` object (here `CustomUserDetails`). However, `#id` is a `Long` (primitive/boxed) and `memberId` is a `Long`. While type matching works, the bigger issue is that `CustomUserDetails` does not expose `memberId` as a standard property accessible via SpEL if the principal is wrapped or if the context is not set correctly. More critically, if `authentication` is null or the principal is an `AnonymousUser`, this may throw an exception or behave unexpectedly. Furthermore, relying on `#id` matching the principal's ID is a common pattern, but it fails if the `CustomUserDetails` object does not correctly expose `getMemberId()` or if the SpEL context cannot resolve `memberId` directly from the principal object without a getter. In `CustomUserDetails`, `getMemberId()` exists, so `authentication.principal.memberId` should work. **However**, the real risk is that `#id` is a path variable. If an attacker sends a request where `#id` matches their own `memberId`, they pass. But if the `MemberService.getMemberById` returns data for *any* member, and the check is only on the ID, it is safe. **Wait**, the actual vulnerability is that `authentication.principal` might not be the `CustomUserDetails` object in all contexts (e.g., if session is restored differently). A safer approach is to inject the `Authentication` object or use `@AuthenticationPrincipal CustomUserDetails user` and compare `user.getMemberId()`. The current SpEL is fragile. |
| F-002 | IDOR Vulnerability: Store/Staff Ownership Validation | P1 | WARN | `StoreAuthorizationService.java` (Lines 33-45, 52-64, 71-83, 90-102) | **Design is Good, Implementation Risk**: The `StoreAuthorizationService` correctly implements ownership checks by querying the DB for the owner ID and comparing it to the current user.
